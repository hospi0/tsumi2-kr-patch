## 3. `.arc` = 자체 NARC 컨테이너 (확정 · 파서 `tools/narc.py`)

빅엔디언. 표본 5개 전부 일치.
```
+0x00 'NARC' | +0x04 u32 항목수 n | +0x08 u32 이름표 «크기» | +0x0C u32 데이터 시작
+0x10 항목 n개 × 16 B : [이름필드폭(0x20) | 이름오프셋 | 데이터오프셋 | 크기]
이름표 = 0x10 + n*16 부터, 데이터는 16 B 정렬
```
★검산 : `데이터시작 − 이름표크기 == 0x10 + n*16` 이 모든 표본에서 정확히 성립.
⛔`+0x08` 을 «오프셋»으로 읽으면 항목표 한가운데를 가리킨다(처음 그렇게 읽고 틀렸다).

내부 블롭 형식 : `bres`(BRRES 모델·텍스처) · `SPRX`(자체 2D 스프라이트) · `REFF`/`REFT`(이펙트).
전체 아카이브의 항목 이름은 **2,228종**.

## 4. 글리프 경로 — `MsgFont.brfnt` (확정)

표준 BRFNT(`RFNT` ver 0104, 6섹션).

| 항목 | 값 |
|---|---|
| 셀 | **26 × 30** · 베이스라인 21 · 최대폭 28 |
| 텍스처 | 시트 **20장** · 각 1024×32 · **IA4**(포맷 2) · 시트당 37칸 |
| 글리프 | **733개** (CWDH 0~732) |
| 전진폭 | 8~28 (가변폭) |

### ★★★인코딩은 Shift-JIS 다
CMAP 3개가 SJIS 코드를 그대로 가리킨다.
| CMAP | 범위 | 방식 | 문자 수 |
|---|---|---|---|
| 1 | `0x0020~0x007B` | 표 | 79 |
| 2 | `0x824F~0x8393` | 표 | 206 (전각영숫자·히라가나·가타카나) |
| 3 | 전 범위 | 스캔 | 448 (`0x8140` 전각공백부터 · 기호·한자) |

### ★★★여유 칸이 0 이다
**매핑된 문자 733 = 글리프 칸 733.** 빈 칸이 하나도 없다.
→ 한글을 넣으려면 **BRFNT 시트를 늘려야** 하고, 그게 되는지가 완성 여부를 좌우한다.
   (게임이 시트 수를 헤더대로 읽는지 실측 필요)

## 5. 텍스트 모집단 — ✅확정 (2026-09-07)

### 찾은 것 : `main.dol` 문자열 풀 `0x2C0000~0x310000`
가나 포함 문자열 **503개 · 전각 5,967자**. 성격은 **UI·시스템**이다.
```
0x2C6F38  １P側コントローラの設定をします。
0x2C97E1  データが上書きされます。
0x2CCA30  ランキングサーバーへの接続に失敗しました

```
`0x2F53AA`·`0x2F546A` 에 **가나표**(히라가나 83자·가타카나 86자) — 이름 입력용으로 보인다.

### ⛔못 찾은 것 : 스토리 대사·자막
- `main.dol` 에 대사가 **없다**.
- 게임 파일 전체(`.arc` 81개 · `.rso` 8개)를 «가나 2자 이상» 필터로 훑어도 **평문 SJIS 대사 0건**.
  상위 파일(`texture.arc` 등)의 검출은 전부 압축 텍스처·모델 바이트의 오탐이었다.
- 아카이브 항목 이름 2,228종에도 `MSG`/`TEXT`/`SCRIPT` 류가 없다. 있는 건
  `FONT02~06` · `MENU_*` · `M_FONT01~03` — **전부 `SPRX` 스프라이트 + `bres` 텍스처**.

### 남은 가설 (아직 어느 것도 확정 아님)
1. **자막이 «구운 그림»** — `texture.arc`(88 MB)의 `FONT*`·`MENU_*` 가 그 후보.
   [[feedback_string_absent_means_baked_graphic]] 의 지문과 맞는다.
2. **대사가 압축돼 있다** — `.arc` 안 블롭이 압축이면 평문 스캔에 안 걸린다.
3. **`.rso` 모듈 안** — `stg00~07.rso` 를 아직 개별 해독하지 않았다.
4. **애초에 자막이 없다** — 음성만이고 화면 텍스트는 UI뿐일 수 있다.

## 5.5 실기·메모리로 확정한 것 (2026-09-07)

### ✅자막은 «진짜 텍스트»다 — 그림 가설 탈락
실기 스샷 : `女を引き渡せ...` · `あぁ、カチ。大丈夫か？` 가 `MsgFont` 서체로 그려진다.
★그림이면 이 폰트가 필요 없다. 폰트에만 있고 UI 엔 안 쓰이는 179자
(`俺 僕 娘 奴 誰 神 魔 聖 邪 話 顔 騒`…)가 **대사 어휘**라는 것과 맞물린다.

### ✅UI·튜토리얼은 `main.dol` 안 · 평문 SJIS · 제어코드 확인
메모리에서 화면 문구를 찾아 **`main.dol` 파일 오프셋까지 확정**했다.
| 화면 문구 | 메모리 | main.dol 파일 오프셋 |
|---|---|---|
| `まずは基本操作をマスターしよう` | `0x802CF7F7` | **`0x2CB8D7`** |
| `コントロールスティック` | `0x802CE0B4` | **`0x2CA194`** |

**★★★제어코드 = `0x01` + RGB 3바이트** (실측)
```
01 FF FF 01  ■ まずは基本操作を…   ← 노랑
01 FF 01 FF  %s                  ← 마젠타(스샷의 분홍)
01 FF FF FF                      ← 흰색
```
`%s` 는 런타임에 버튼 이름이 끼워지는 자리다([[feedback_placeholder_expands_at_runtime]]).
⛔`0x01` 뒤 3바이트는 «글자가 아니다» — 추출·되넣기에서 반드시 토큰으로 보존해야 한다.

### ⛔대사는 `main.dol` 에도 없다
대사 어휘(`俺僕娘奴誰神魔聖邪…`)를 쓰는 문자열이 **튜토리얼 한 줄뿐**이다
(`0x2CC20C ■ アイテムを取り逃がすな！ ■`).
→ 자막 텍스트는 **런타임에 «따로 적재»된다.** 컷신이 아닌 상태에서는 MEM1/MEM2 에도 없다.

## 5.6 컷신 «일시정지» 상태 메모리 조사 (2026-09-07)

화면 : `システムオールグリーン。大気圏突破まで、あと３０秒` 가 떠 있는 상태로 정지.

| 검사 | 결과 |
|---|---|
| MEM1(24MB)+MEM2(64MB) 에서 SJIS·UTF-16(BE/LE)·UTF-8 전수 | **0건** |
| 두 글자 연속(`大気`·`気圏`·`突破`…) | **0건** — 글자가 «나란히» 있지도 않다 |
| `大` 뒤 24 B 안에 `気` (사이에 다른 바이트가 낀 경우) | **0곳** |
| 글리프 번호 u8/u16BE, 간격 128 B 까지 | 잡음뿐 |
| `texture.arc` 159항목에 자막스러운 이름 | **0개** |

### ✅확인된 것 — 폰트는 MEM2 에 올라와 있다
`MsgFont` 의 **텍스처가 `0x9330F150`** 에 그대로 있다(RFNT 헤더는 없음 — 게임이 컨테이너를
버리고 텍스처만 올린다). ★디코더 검증 : 시트0 을 IA4 로 풀면 `!"%'()*+-./0123456789…ABCDEFGHIJKL`
가 정확히 나온다(`tools` 밖 일회용 스크립트, `work/_font_sheet0.png`).

### ⚠️그래서 남은 것
자막 문자열이 **RAM 어디에도 «텍스트로» 존재하지 않는다.** 그런데 폰트는 올라와 있다.
남은 설명은 둘뿐이다.
1. 적재 시점에 **곧바로 정점/쿼드(그리기 명령)로 변환**되고 원문 버퍼는 해제된다.
2. 자막이 **컷신 전용 텍스처**인데 이름 규칙이 달라 못 찾았다.

### ✅텍스처 덤프 결과 — 자막은 «구운 그림»이 아니다
`Dump/Textures/R2VJ01` 496장이 **전부 `608x456`·`304x228`** = EFB 복사본(프레임버퍼)뿐이고,
자막 크기의 전용 텍스처가 **0장**이다. → 자막은 **폰트에서 글자 단위로 그려진다**(가설 2 탈락).

### ⛔그런데 «그릴 글자»가 RAM 어디에도 없다 — 추가 배제
`システムオールグリーン` 을 다음 형태로 MEM1+MEM2 전수 검색 : **전부 0건**
- 글리프 번호 u16BE / u8
- SJIS u16 **리틀엔디언** / SJIS u32BE

### ★다음 실험 (이전 계획 — 텍스처 덤프는 위에서 이미 수행)
돌핀 그래픽 설정에서 **«텍스처 덤프»** 를 켜고 그 컷신을 다시 재생한다.
- 덤프에 «자막 글자가 통째로 그려진 이미지»가 나오면 → 2번(구운 텍스처). 그래픽 작업이 된다.
- 폰트 시트만 나오고 자막 이미지가 없으면 → 1번. 텍스트 원본을 찾으려면
  **적재 코드(폰트로 그리는 루틴)를 역추적**해야 한다.

## 5.9 ★★★자막 = 「구운 그림」이 맞다 — 모집단 확정

사용자가 찾아 준 참고 자료(`my files/Wii - Sin & Punishment... Game Dialogue`)가 결정타였다.
자막이 **PNG 이미지**로 정리돼 있고(영어·프랑스어·스페인어·일본어 4개 언어), 그 이름이
디스크의 항목 이름과 **정확히 일치**한다.

⛔내 실수 : 자막스러운 이름을 `DEMO|MSG|SUB|TELOP…` 으로 찾다가 **접두 `TX` 를 놓쳤다.**
  이름 접두 통계에 `TX 39개` 가 이미 찍혀 있었는데 지나쳤다.

### 구조 (확정)
```
스테이지 아카이브   s01dat00.arc 의 «TX1_1»  = SPRX (스프라이트 정의)
                        ↓ tx1_1_01.tga … 파일명으로 참조
texture.arc         «TX1_1_01» = bres → TEX0 (실제 그림)
```
- **SPRX** : `+0x04` 바이트0 = 텍스처 수 · 바이트1 = **스프라이트 수(=자막 줄 수)**,
  `+0x20` 부터 텍스처 파일명(16 B 고정), 그 뒤 인덱스표와 쿼드 좌표(float).
- **TEX0** : `512×512` / `512×256` / `512×128` / `512×64` · **fmt=2 (IA4)** · mip=1.
  한 장에 여러 줄이 «가운데 정렬»로 세로 나열된다. 루비(후리가나)도 그림에 포함된다.

### 모집단
| | |
|---|---|
| 자막 텍스처 | **39장** (`texture.arc`) — 전부 IA4 |
| 자막 줄 | **270줄** (SPRX 19개의 스프라이트 수 합) |
| 스테이지 | `TX0`~`TX7` (s00~s07) |

★참고 자료의 일본어 44장 중 5장(`TX4_3SUB_JP`·`TX4_4SUB_JP`·`TX5_3SUB_JP`·`TX6_4_04`·`TX7_0_01`)은
  디스크에 **없다** — 다른 리비전/미사용으로 보인다. 우리 기준은 디스크의 39장이다.

### ✅이 발견이 앞의 모순을 전부 설명한다
- 자막 문구가 SJIS·UTF·글리프번호 어느 형태로도 **디스크·RAM 에 없던 이유** = 텍스트가 아니라 그림
- 텍스처 덤프에 자막이 없던 이유 = 이미 캐시됐거나 EFB 만 덤프됨
- `MsgFont.brfnt` 733자는 **UI·튜토리얼 전용**이다

### 작업 성격
| 대상 | 형태 | 작업 |
|---|---|---|
| **컷신 자막 270줄** | IA4 텍스처 39장 | **그래픽 텍스트** — 이미지를 다시 그린다 |
| **UI·튜토리얼** | `main.dol` 평문 SJIS + 제어코드 `0x01`+RGB | 일반 텍스트 |
| **폰트** | `MsgFont.brfnt` 733칸, 여유 0 | UI 용 한글 글리프 공급 |

★**영어·프랑스어·스페인어 판이 실제로 존재**한다 = 같은 자리에 다른 언어를 넣어도
  게임이 도는 것이 이미 증명돼 있다. IA4 회색조라 팔레트 문제도 없다.
⛔단 «디스크의 39장을 교체해 실기에서 바뀌는지»는 아직 검증 안 했다.

## 9. ★★★파일↔메모리 델타는 «하나»가 아니다 (세션2 최종 수정)

`イサ` 를 번역표에 넣고 빌드했는데 화면이 **그대로 원문**이었다. 원인은 배포 쪽이었다.

`main.dol` 섹션 표(`tools/dol.py`) :
```
 sec  파일        메모리        크기      delta
 11   0x2C3DA0  0x802C7CC0  0x014540  0x80003F20   ← UI 문자열 풀
 12   0x2D82E0  0x802DC200  0x03D160  0x80003F20
 13   0x315440  0x80460320  0x002240  0x8014AEE0
 14   0x317680  0x804634E0  0x003260  0x8014BE60   ← 이름·라벨 고정폭 표
```
- `0x80003F20` 은 **섹션 11·12 의 값**일 뿐이다. `0x318C70`(イサ)은 섹션 14 라
  올바른 주소가 `0x80464AD0` 인데, 단일 델타로는 `0x8031CB90` — **BSS 한복판**이다.
  게임이 BSS 를 지우므로 아무 일도 안 일어나고 화면은 원문 그대로 남는다.
- ⛔같은 실수가 «참조 census» 에도 있었다. 섹션 13·14 를 가리키는 포인터를 되돌리지
  못해 그 구간 문자열이 census 에 아예 안 잡혔다(보호 집합도 그만큼 비었다).

수정 : `tools/dol.py` 를 만들어 `mkriiv.py`·`uipatch.py` 둘 다 **섹션별 매핑**을 쓴다.
`mkriiv.py` 는 구간이 섹션 경계를 넘거나 섹션 밖이면 **빌드를 실패시킨다**.
검산 : XML 의 `<memory>` 107개를 «메모리 주소 → 파일 오프셋»으로 되돌려
빌드 결과와 대조 — 불일치 0.
